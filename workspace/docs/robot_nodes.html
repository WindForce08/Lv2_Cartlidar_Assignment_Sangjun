통신 방식

카드와 표의 색 태그가 어떤 방식으로 만들지 알려줍니다. Server는 기능을 실행하는 쪽, Client는 요청하는 쪽입니다.

종류동작보내는 쪽 → 받는 쪽rclcpp에서 만드는 법예
Topic계속 흘려보냄, 응답 없음 (1:N)Publisher → Subscribercreate_publisher<T>() / create_subscription<T>()/arm_range
Service요청 1번 → 응답 1번, 바로 끝남Client → Servercreate_client<T>() + async_send_request() / create_service<T>()/perception/set_mode
Action목표 → 진행 상황 → 결과, 취소 가능Client → Serverrclcpp_action::create_client · create_server/manipulator/pick
  • 모든 직접 구현 노드는 rclcpp::Node 상속 + RCLCPP_COMPONENTS_REGISTER_NODE (main 없음).
  • Action · Service 결과를 콜백 안에서 기다리지 않습니다. async 호출 + 콜백으로 처리합니다.
  • 명령 주체는 하나: 바퀴 명령은 drive_node만, 팔 · 그리퍼 명령은 manipulator_node만 보냅니다.
  • /cmd_vel 계열은 TwistStamped (Lyrical).
  • 센서 · 인식 값은 header.stamp(ROS 시계 촬영 시각)가 300ms보다 오래되면 쓰지 않습니다.
  • 통신 정의는 동결 상태: 바꾸려면 docs/interfaces.md PR + Controller 팀장 승인.

  • READ_TAG: Arducam 영상에서 AprilTag 검출 (tag36h11 추정) → tag_id · tag_pose, 카메라 내부 파라미터로 자세 추정

  • stamp = 촬영 시각 (ROS 시계 기준) — 받는 쪽 300ms 규칙의 기준
  • 부하: SEARCH_FRONT | ARM_ALIGN에서 검출 2번(D435 + Arducam)을 15Hz 이상 — 1주차 측정, 부족하면 Arducam 검출 해상도 · 모델 축소

구현 로직

  • /mission/start: IDLE · DONE · FAILED면 새로 시작, PAUSED면 현재 단계부터 재개 (E-stop · 진단 오류가 남아 있으면 거절)
  • /mission/stop: goal 전부 cancel → IDLE, set_mode(OFF)
  • 공통 시작: pose(TAG_VIEW) → read_tag. 2s 안에 태그가 없으면 제자리 30° 회전 (/drive/navigate에 같은 위치 + yaw — drive가 spin으로 처리, TF map→base_link), 최대 11번
  • tag_id → 미션표 (ROS 파라미터 missions.tag_<id>) 단계 실행: navigate · search · approach · pick · pose · skill
  • search: pose(STOW) 완료 후 (재시도 때 팔이 펴져 있어도 D435를 가리지 않게) set_mode(OFF) → set_mode(SEARCH_FRONT | SEARCH_REAR) (OFF로 perception 대상 · manipulator 기억 초기화), 2s 안에 못 찾으면 제자리 45° 회전 (search.rotate_step), 최대 4번 (앞뒤 D435가 각 ~87°라 180°면 한 바퀴) → 없으면 실패. 찾으면 물체 방향으로 spin (후방에서 찾았어도 전방이 향하게) → SEARCH_FRONT로 다시 확인
  • approach <거리>: ① pose(STOW) 완료 후 (이미 STOW면 생략) set_mode(SEARCH_FRONT) → /drive/align <먼 거리> (= max(READY 팔 끝 돌출 + <거리> + 여유 0.1m, align.coarse_min 0.3m), 범퍼 기준) ② pose(READY) ③ set_mode(SEARCH_FRONT | ARM_ALIGN) → /drive/align <거리> (정밀), pick까지 같은 모드
  • skill: set_mode(단계의 mode=, 없으면 SEARCH_FRONT | ARM_ALIGN) → execute_skill. 작성법: mode=이름+이름 (예: mode=SEARCH_FRONT, mode=SEARCH_FRONT+ARM_ALIGN, mode=OFF), 숫자 불가
  • skill 실패 → fallback 단계로 대체 (한 번), pick 실패 · grasped=false → 직전 search부터 재시도
  • /e_stop=true · /diagnostics ERROR → goal 전부 cancel → PAUSED (자동 재개 없음). 진단은 이름이 opencr/로 시작하는 항목만 본다 (diagnostics.name_prefix). opencr 진단이 3s 동안 안 오면 ERROR로 본다 (diagnostics.timeout — 발행 확인 전에는 0)
  • /mission/status 2Hz + 변경 시, result는 header.stamp 300ms 지나면 버림
  • 단계별 타임아웃 · max_retries 초과 → FAILED, 끝나면 set_mode(OFF)

구현 로직

  • result · /arm_range는 header.stamp가 300ms보다 오래되면 버림
  • /drive/navigate: 목표가 현재 위치와 xy_goal_tolerance(0.25m) 이내면 yaw 차이만큼 nav2 spin (target_yaw), 아니면 navigate_to_pose로 전달. feedback 중계, cancel 시 nav2도 cancel
  • /drive/align 모드는 goal을 받은 뒤 한 번 정하고 끝까지 유지: goal 수신 시각 이후 stamp인 첫 result(0.5s 안에 없으면 abort)의 mode에 ARM_ALIGN 비트가 있으면 정밀, 없으면 먼 거리 (mission이 단계마다 모드를 켜서 고름). 정밀 중 offset이 무효여도 먼 거리로 바꾸지 않음 — READY 팔을 편 채 범퍼 기준으로 다가가면 충돌
  • 안전 확인: 먼 거리 모드인데 target_distance < align.coarse_min (0.3m)이면 goal 거절 (설정 실수로 팔을 편 채 가까이 가는 것 방지)
  • 먼 거리: object_pose(D435)로 물체 쪽 회전 + 전진, 거리 = object_pose.x − base.front_offset (범퍼 기준) → target_distance에서 정지. 이미 더 가까우면 후진해서 맞춤. 팔은 STOW라 D435를 가리지 않음
  • 먼 거리 안전: 전진 중 /scan 전방 ±20°에 물체보다 0.1m 이상 가까운 점, 후진 중 후방 ±20°에 0.3m 이내 점이 있으면 정지 후 abort (직접 P제어라 nav2 회피가 없음), 속도 상한 align.coarse_max_speed
  • 정밀 (20Hz): arm_offset → 좌우 · 회전, /arm_range(TFmini, 팔 끝 기준) → 전후 P제어 → /cmd_vel_drive
  • 허용오차 안에서 N주기 유지되면 0 속도 발행 후 success
  • 바퀴 명령은 한 번에 하나: 새 goal이 오면 이전 goal 취소
  • 물체 놓침 (현재 모드의 값이 무효) 0.5s 이상 → 정지 후 abort. 정밀 시작 직후 Arducam이 물체를 찾을 때까지도 같은 0.5s 기준
  • target_distance: 먼 거리는 범퍼 기준, 정밀은 TFmini 기준 (≥ 0.10m, TFmini 최소 측정 거리)
  • execute_skill: rate_hz마다 관측 (/scan · /odometry/filtered · /perception/result) → 추론 → 속도로 변환 → /cmd_vel_drive (align · skill 공용)

PolicyRunner · ObservationBuilder — 노드 아님, drive · manipulator가 링크 · CPU 추론

사용 패키지

  • ONNX Runtime (CPU) · yaml-cpp · Eigen3

제공 클래스

  • PolicyRunner: .onnx 로드 · run(obs) → action (CPU, MLP 기준 1ms 미만)
  • ObservationBuilder: policies.yaml 순서대로 정규화된 float 벡터. 선택 항목은 [값..., valid] 를 붙여서 배치, 무효면 fill(학습 때 안 보이는 경우와 같은 값). 시작 시 obs_dim과 ONNX 입력 차원 비교 → 다르면 로드 실패
  • ActionMapper: 출력 벡터 → 관절 목표(rad) 또는 속도(m/s, rad/s), 범위 clamp

구현 로직

  • policies.yaml 파싱: model(.onnx) 경로 · rate_hz · observation · action · 정규화 값

  • GPU는 perception 전용: ⑧ 컨테이너에 CUDA 컨텍스트를 만들지 않음
  • gtest: 고정 입력 → 학습 쪽에서 받은 기대 출력과 비교 (sim-to-real 1차 확인)
  • gtest: obs_dim · 배치 순서 · fill 검사 (학습 쪽 예제 벡터와 비교)
  • 학습 쪽 요청: 선택 관측은 시뮬레이션에서 일부러 끊어(dropout) valid 0 상황도 학습 — 안 하면 실물에서 처음 보는 입력

미션 · 강화학습

태그를 읽으면 미션표에서 단계 목록을 찾고, skill 단계는 지정한 정책으로 실행합니다. 정책은 학습 담당(Isaac Lab)이 ONNX로 주고, Jetson에서 ONNX Runtime으로 CPU 추론합니다.

# mission_table.yaml  (Controller 팀, mission_node ROS 파라미터) — 공통 시작 pose(TAG_VIEW) → read_tag 뒤에 붙음
locations:
  names: [home, station_A]
  home: [0.0, 0.0, 0.0]          # = slam_toolbox map_start_pose
  station_A: [1.0, 0.0, 0.0]
missions:
  tag_ids: [7, 12]
  tag_7: ["navigate station_A",           # 주행 + 팔 STOW (병렬)
          "search",                        # SEARCH_FRONT | SEARCH_REAR, 못 찾으면 45°씩 최대 4번 회전
          "approach 0.15",                 # STOW로 D435 접근 (READY 돌출 + 0.15 + 0.1) → READY → Arducam · TFmini 정밀 0.15m
          "skill manipulator pick_cup_v1 fallback=pick",
          "navigate home"]
  tag_12: ["skill drive slalom_v1 40 mode=SEARCH_FRONT fallback=navigate:station_A",   # mode=이름+이름, 없으면 SEARCH_FRONT+ARM_ALIGN
           "pose STOW", "navigate home"]
# policies.yaml  (학습 담당이 ONNX와 함께 제공) — CPU 추론 (ONNX Runtime)
# 벡터 배치: observation 순서대로, required 항목 = [값...], 선택 항목 = [값..., valid] (valid 1 = 유효, 0 = fill 사용)
# fill = 학습(시뮬레이션)에서 안 보일 때 넣은 값과 같게. obs_dim이 ONNX 입력 차원과 다르면 로드 실패
pick_cup_v1:
  model: models/pick_cup_v1.onnx     # 노드 시작 시 로드, 변환 없음
  rate_hz: 20
  obs_dim: 12                        # joint_pos 6 + arm_offset (3 + valid 1) + arm_range (1 + valid 1)
  observation:
    - {name: joint_pos, size: 6, required: true}
    - {name: arm_offset, size: 3, required: false, fill: [0.0, 0.0, 0.0]}
    - {name: arm_range, size: 1, required: false, fill: [12.0]}   # 안 보임 = 최대 거리 (0은 "아주 가까움"이라 금지)
  action: joint_target(6)             # rad, 관절 한계로 clamp
slalom_v1:
  model: models/slalom_v1.onnx
  rate_hz: 20
  obs_dim: 367                       # scan 360 + odom_twist 3 + object_pose_base (3 + valid 1)
  observation:
    - {name: scan, size: 360, required: true}
    - {name: odom_twist, size: 3, required: true}
    - {name: object_pose_base, size: 3, required: false, fill: [0.0, 0.0, 0.0]}   # base_link 기준 물체 위치 (D435)
  action: base_twist(2)               # vx (m/s), wz (rad/s)

결정이유
영상은 토픽으로 보내지 않는다perception_node가 카메라 3대를 SDK로 직접 열고 결과만 /perception/result로 발행합니다. 영상 직렬화 · 복사 비용이 없어 Jetson 부하가 크게 줄어듭니다.
명령 주체는 하나바퀴 명령은 drive_node만, 팔 · 그리퍼 명령은 manipulator_node만 보냅니다. 여러 노드가 같은 모터에 명령해서 충돌하는 일을 막습니다.
mission은 순서만 정한다실행은 drive · manipulator가 Action 서버로 맡고, mission은 Action을 보내기만 합니다. 그래서 주행과 팔 동작을 병렬로 겹칠 수 있습니다.
정밀 정렬은 READY 후, 먼 거리는 STOWTFmini와 Arducam이 팔 끝에 있어서 팔이 움직이는 동안에는 값이 바뀝니다. 먼 거리 접근은 팔을 STOW로 접은 뒤 D435로, READY가 끝난 뒤 정밀 정렬. 병렬은 주행 중 팔 접기처럼 센서와 무관한 동작에만 씁니다.
perception 모드는 비트 플래그SEARCH_FRONT · ARM_ALIGN처럼 필요한 결과를 함께 켭니다. 정렬 중에도 object_pose가 갱신되고, 필요 없는 카메라(후방)는 꺼서 GPU를 아낍니다.
300ms 규칙 · ROS 시계 stamp인식 · 거리 값은 촬영 시각(ROS 시계) 기준 300ms가 지나면 쓰지 않습니다. 오래된 값으로 제어하면 로봇이 진동합니다. perception은 ARM_ALIGN에서 15Hz 이상.
E-stop은 opencr_hardware 한 곳 · 잠금식조이스틱 heartbeat(0.5s) · E-stop 버튼 · 물리 스위치(필수) 중 하나면 정지합니다. 리셋 버튼으로만 풀리고, 미션은 시작 버튼을 눌러야 재개합니다. 자율 주행 중에도 조이스틱은 켜 둡니다.
진단은 opencr 항목만/diagnostics에는 다른 패키지(controller_manager 등)도 진단을 냅니다. OpenCRHardware는 이름을 opencr/<항목>으로 붙이고, mission은 이 항목만 보고 멈춥니다. 진단이 3s 동안 안 와도 멈춥니다.
200ms와 300ms는 다른 규칙200ms = 펌웨어가 Jetson 명령을 못 받으면 바퀴를 세우는 안전 타임아웃. 300ms = ROS 노드가 인식 · 거리 값을 믿을 수 있는 최대 나이. 서로 바꾸지 않습니다.
skill 단계도 perception을 켠다강화학습 정책은 object_pose · arm_offset을 관측으로 씁니다. mission은 skill 전에 단계의 mode=(없으면 SEARCH_FRONT | ARM_ALIGN)를 켭니다.
align 모드는 goal마다 고정drive는 goal을 받은 뒤 처음 오는 새 result의 ARM_ALIGN 비트로 먼 거리 · 정밀을 정하고 바꾸지 않습니다. 정밀 중 값이 잠깐 끊겼다고 먼 거리로 바꾸면 팔을 편 채 범퍼 기준으로 다가가 부딪힙니다. 먼 거리 접근은 nav2 회피가 없어서 /scan으로 앞 장애물을 봅니다.
접근은 2단계 · 팔 STOW에서 시작팔 끝 Arducam · TFmini는 가까이 가야 물체가 보이고, READY 팔은 D435를 가릴 수 있습니다. 그래서 팔을 STOW로 두고 D435로 먼 거리까지 → READY → Arducam · TFmini로 정밀 정렬합니다. 먼 거리 = max(READY 팔 끝 돌출 + 정밀 목표 + 0.1m, 0.3m)라 팔을 펴도 물체에 닿지 않고, 이미 더 가까우면 후진해서 맞춥니다. 뒤에서 찾은 물체는 먼저 spin으로 전방을 향합니다.
제자리 회전은 nav2 spin시작 위치 = 목표 위치인 navigate_to_pose는 경로가 안 나오거나 회전 없이 성공할 수 있습니다. drive_node가 위치 차이가 xy_goal_tolerance 이내인 목표를 spin으로 바꿔 처리합니다 (위치 보정으로 몇 cm 튀어도 spin).
nav2 최종 출력만 /cmd_vel_navspin · backup은 behavior_server가 직접 속도를 냅니다. controller · behavior_server → velocity_smoother → collision_monitor 체인의 마지막 출력만 /cmd_vel_nav로 보내야 twist_mux의 E-stop 잠금을 거치고, 같은 토픽에 발행자가 둘 생기지 않습니다.
물체 하나만 따라간다PerceptionResult에는 물체가 하나뿐이라 perception이 고릅니다: 차체 · 그리퍼 영역(exclude_box) 밖, 신뢰도 기준을 넘는 것 중 가장 가까운 것. 고른 뒤에는 직전 위치 0.3m 안의 검출만 같은 물체로 봅니다. mission이 search마다 OFF를 보내 대상과 manipulator 기억을 함께 초기화합니다.
valid 플래그는 학습에서도시뮬레이션에서 관측을 일부러 끊어 valid 0 상황을 학습시켜야 실물에서 값이 사라져도 정책이 버팁니다.
pick 목표 우선순위① 정밀 정렬 결과 (Arducam 중심 + TFmini 거리, 새 값) ② 새 D435 object_pose ③ SEARCH_FRONT가 켜진 동안 odom 기준으로 기억한 위치. ③만 300ms 규칙의 예외입니다.
관측 무효 규칙은 학습과 같게물체가 안 보이는 게 정상인 정책도 있습니다. 선택 항목은 [값..., valid]로 배치하고, 무효면 학습 때 안 보일 때 넣은 fill 값을 씁니다. obs_dim이 ONNX 입력과 다르면 로드하지 않습니다.
ekf 회전은 IMU만4륜 스키드 방식은 회전할 때 바퀴가 미끄러져 바퀴 회전 속도가 부정확합니다. ekf는 바퀴에서 전진 속도만, 회전 속도는 IMU에서 받습니다.
정책 추론은 CPU강화학습 정책은 작은 MLP라 ONNX Runtime CPU로 충분합니다. GPU · CUDA는 perception만 써서 메모리를 아끼고 충돌을 막습니다.
TF는 변환마다 발행자 하나odom→base_link는 ekf만 발행합니다 (diff_drive_controller는 enable_odom_tf: false). 두 노드가 같이 내면 위치가 튑니다.
C++ component · 프로세스 8개직접 구현 노드는 모두 rclcpp component입니다. 같은 컨테이너 안은 복사 없이 통신하고, 바퀴 · 팔 콜백이 실제로 병렬로 돕니다. 배치는 launch만 바꾸면 됩니다.
Lyrical 기준/cmd_vel 계열은 TwistStamped, 그리퍼는 parallel_gripper_action_controller (ParallelGripperCommand)를 씁니다.
통신 정의 변경 규칙토픽 · Action · Service · 메시지 정의는 동결 상태입니다. 바꾸려면 docs/interfaces.md에 PR을 올리고 Controller 팀장 승인을 받습니다. robot_interfaces 소유는 Controller 팀입니다.
